The question, not the pipelines

Four ways to sort payment disputes into nine categories, each more sophisticated and more expensive: a rules engine, one LLM call, RAG, a multi-agent graph. You measure all four on the same set, with the same harness and the same model.

The deliverable is the comparison: where does the next step of sophistication pay for itself?

Check yourself: what's the one sentence this project lets you say?

“I'd start with the cheapest thing that could work, measure it against a labelled set, and only escalate where the error cost justifies it. I have the numbers from doing exactly that on dispute triage.”

2

Build the eval set first, labelled blind, twice

The seed has 180 disputes in four tiers: clear, paraphrase, policy conflict, stated-reason-wrong. They were drafted and labelled by Claude, so they aren't yours yet. Rewrite the definitions, extend toward 420 cases, then label every case blind, again a day later, and freeze.

python tools/label.py pass1
python tools/label.py pass2 && python tools/label.py agree && python tools/label.py freeze

Labelling after building pipelines turns a measurement into a certificate. Your self-agreement rate is the ceiling: the dashed line on every accuracy chart.

Check yourself: why split dev and test?

You tune rules, prompts and k on dev (30%) and report test (70%). Tuning on the numbers you report is overfitting. At about 130 test cases the 95% interval is roughly ±8 points, so smaller differences are noise.

3

Rung A: the rules engine

Regex per category in pipelines/rules.toml, first match wins, no model. Unmatched disputes go to a human. Right now it scores 49.6% on test. Tune it on dev until adding patterns stops helping (about 60% is the honest ceiling).

python run_eval.py --pipeline rules

Rules match words; disputes are paraphrase. Open the console, press ⚡ Red-team it, and watch Hinglish, typos and SMS-speak break the patterns live.

Check yourself: why does rules have the highest fixed monthly cost?

Someone has to edit rules.toml forever as customers' wording drifts. That maintenance is real money ($400/month in our assumptions), even though each call costs $0.

4

Rung B: one LLM call

One prompt with the nine definitions, output forced through a tool schema whose category is an enum, so there's no string parsing. Anything outside the enum is counted as a parse error, never guessed. Zero-shot first, few-shot later as a measured delta.

python run_eval.py -p single --estimate
python run_eval.py -p single --yes

The A→B gap is the most valuable number in the project: it tells a client whether AI is worth starting at all. Under 10 points means your eval set is too easy.

Check yourself: the free tier stops your run at case 120. What happens?

The harness saw the daily-cap 429, checkpointed every finished case to runs/single.jsonl, and stopped. Run the same command tomorrow and it resumes at case 121. Nothing is paid twice.

5

Rung C: RAG over written policy

Retrieve the top-k policy rules and put them in the prompt. The corpus is 46 documents chunked by document, one rule each. Hybrid search fuses BM25 (exact terms) with embeddings in pgvector using Reciprocal Rank Fusion. Tune k ∈ {1, 3, 5, 8} on dev.

pip install fastembed "psycopg[binary]" && python tools/ingest_pgvector.py
RAG_K=5 python run_eval.py -p rag --split dev --yes
Check yourself: RAG got a case wrong. What two different things could have happened?

Retrieval missed (no retrieved doc spoke about the right category: fix search) or the model ignored good context (fix the prompt). The Failure modes section counts both separately.

6

Rung D: agents, and E: a small-model cascade

D: the classifier proposes, the verifier checks the category's qualifying conditions, and the arbiter runs only when the verifier rejects. It can route to a human, so automation rate becomes a third dimension. E is an agentic routing experiment: llama-3.1-8b-instant answers first and escalates to the 70B + RAG only when unsure. It mixes models, so it sits beside the ladder, not on it.

python run_eval.py -p agents --yes
CASCADE_THRESHOLD=0.85 python run_eval.py -p cascade --split dev --yes
Check yourself: what makes D multi-agent rather than a long prompt?

The conditional edge: the arbiter only runs on rejection. An unconditional three-call chain costs about 40% more and isn't a system that decides anything. And an 8B model's confidence is poorly calibrated, which is why E's threshold is tuned on dev, not trusted.

Read the dashboard like a skeptic

The Skeptical reviewer section audits your results live: seed labels, overlapping intervals, tiny tiers, dev≫test, stale prices. It gives an interview-readiness score out of 100 (see the dashboard). The cost model turns accuracy into money with a client's volume, error cost and review cost (₹ supported). Autopilot operates the console for you: flip it on and watch.

Fix every red before you quote a number. Each red is a question you'd lose in an interview.

Check yourself: RAG 86% [79–92] vs agents 88% [81–93]. Who wins?

Nobody, at this n: the intervals overlap. You say “agents bought about two points for several times the cost, within the noise”, then show where the cost model says that's still worth it.

8

Ship it, then sell the method

Deploy overkill/web on Vercel (Root Directory = overkill/web, framework “Other”). It's static, so it's never down. Write the README's finding in two sentences. Post the finding weekly, not the build.

Then turn it into an AI Build Decision Review: their task, 100–200 cases labelled by their team, cheapest-first benchmark, cost model with their numbers, a one-page recommendation and this dashboard as the live artifact.

Check yourself: a founder asks what you'd build for them.

“The cheapest thing that could work, measured against your labelled cases, escalating only where your error cost pays for it. Here's the dashboard from doing exactly that on dispute triage.” Price against the overbuild you prevent, not your hours.
